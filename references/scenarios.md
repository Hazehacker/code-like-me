# 应用与反例

用于遇到取舍时参考，以及后续回归检查。这里描述决策与可观察结果，不是统一项目模板。本轮实际做过的检查见 [验证记录](validation.md)。

## 新增 Spring 业务类

即使附近的旧代码仍使用字段注入，只要项目没有相反的明确约定，新增类使用构造器注入。已有 Lombok 时使用 `@RequiredArgsConstructor` 与 `private final`。这来自主动规范化记录；单次增加方法不触发全项目迁移。

例如新增分类别名用例：Service 校验分类存在与别名冲突，调用 Mapper 写入；沿用现有业务异常与消息常量。方法名表达 `addAlias`。若需要唯一性保证，验证数据库约束或其他原子机制，不能把“先查再插”描述为并发安全。

## 单个列表增加筛选

需求：文章列表增加 `tagId`，已有 `Result<PageResult>` 和 `ArticleShortVO`。

沿现有入口、Service 和 Mapper 增加参数与条件，保留列表输出。确认关联表是否造成文章重复，以及分页总数是否仍正确。只有这一个查询需求时，不建立 `BaseCrudService<T, Q, V>`。这与使用项目已经稳定的通用能力不冲突。

## 关系变化和资源生命周期

需求：从一个歌单移除歌曲；歌曲可被多个歌单引用。

先查产品契约和关联关系，确定本次动作是否仅解除关联。Service 承接规则，Mapper 执行对应关系修改。不要从名字相近的历史实现推导“移除关联就是删除实体”。验证其他歌单与歌曲资源是否应保留；不要顺带新增或改变用户未要求的权限模型。

需求：同一资源的多个入口都存在已证实的一致性缺陷。

先找共同原因和授权范围。在当前修复范围内，让各入口调用同一业务语义或补齐相关事务边界，可以比多处打补丁更省后续成本。不同语义仍保持各自归属；不用一个 `execute(Object, Map)` 掩盖差异。旧脏数据是否清理是另一项有副作用的动作，不由代码修复自动授权。

## 外部上传失败

需求：上传文件成功后才能保存可用资源记录。

失败应保留真实错误语义；`finally` 仅承担需要保证执行的清理，不从中返回业务成功。数据库事务与对象存储之间先明确一致性需求，再选择失败清理、重试或其他已有机制。不要因为某个历史类这样写就复制异常路径。

## 新技术栈

需求：用 Go 写一个小工具，或者调整 Vue 页面的展示状态。

沿目标项目的习惯组织代码。先确定状态所有者、调用边界、错误与清理路径；不迁入 Java 的 ServiceImpl/DTO 全套层次，也不因曾使用 Redis、MQ、微服务就自动添加这些依赖。

## 变更完成时

报告实际行为、选择背后的关键理由和真实验证结果。对只读分析说明没有运行；对页面说明检查了哪个状态；对业务变更说明失败路径、关联数据或兼容性检查覆盖到哪里。验证规模与改动风险匹配，不用机械流程增加无效成本。
